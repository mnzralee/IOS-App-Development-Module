Architecture Part 2 App Map

Learning Objective Read the architecture before writing code. Identify which object owns each piece of state, how Views communicate with ViewModels, how navigation works, and why the Part 2 additions do not require a redesign of Part 1.

How to read the diagram

Screen: a user-facing destination such as MovieListView, MovieDetailView, AddMovieView, or SettingsSheetView.

Sub-View: a smaller View that forms part of a screen. For example, the detail screen contains header, metadata, synopsis, and action Views.

Reusable component: a View designed to be used in more than one place, such as GenreBadgeView or RatingView. It renders values passed to it; it does not own application state.

Model: describes movie data. Movie is still a plain Swift struct in Part 2, and Genre is the top-level domain enum in Movie.swift. MockDataStore remains the in-memory source.

ViewModel: owns mutable application/form state and user-intent methods. MovieListViewModel owns the movie list and search state; AddMovieViewModel owns the Add Movie form state and validation.

View: renders state and sends user intentions. It should not contain the filtering or movie-list mutation logic.

Data flow: MockDataStore → MovieListViewModel → MovieListView. A search edit changes searchText; the computed filteredMovies changes; SwiftUI re-renders. Adding a movie travels back through the onSave callback to the parent ViewModel.

Part 1 → Part 2 → Part 3

Part 2 adds interaction around the same foundation. The important architectural point is that MockDataStore remains the source of movie data. Part 3 will replace the in-memory mechanism with SwiftData without moving filtering and presentation responsibilities into the Views.

App UserPreferences — Global App State

Create App/UserPreferences.swift. This @Observable class stores app-wide settings needed by multiple screens. It is kept in memory for Part 2; persistence of app data is introduced in Part 3.

📐 Why environment injection?

If appearance were stored inside MovieListViewModel, the Settings sheet would need a direct reference to it. Environment injection is the SwiftUI-idiomatic alternative: one object placed in the environment tree, readable anywhere below the injection point.
App/UserPreferences.swift
import SwiftUI
import Observation

@Observable
final class UserPreferences {

    // Appearance selection held in app state (not persisted to disk in Part 2)
    var colorSchemePreference: ColorSchemePreference = .system
    var displayName: String = "My"

    // Converts the enum to the optional ColorScheme SwiftUI expects
    var preferredColorScheme: ColorScheme? {
        switch colorSchemePreference {
        case .light:  return .light
        case .dark:   return .dark
        case .system: return nil
        }
    }

    enum ColorSchemePreference: String, CaseIterable {
        case light  = "Light"
        case dark   = "Dark"
        case system = "System"

        var icon: String {
            switch self {
            case .light:  return "sun.max"
            case .dark:   return "moon.stars"
            case .system: return "circle.lefthalf.filled"
            }
        }
    }
}

Important: this is app state, not persistence

@Observable makes changes visible to SwiftUI. It does not save these values between launches. Closing and relaunching the app resets the values. SwiftData persistence is introduced in Part 3.

Common mistakes

  • Using ObservableObject and @Published instead of Observation.
  • Forgetting import Observation when using @Observable.
  • Treating @Observable as persistence. It is observation, not storage.

App Update the App Entry Point

Update App/MovieGenreFilterApp.swift to create a UserPreferences instance and inject it into the environment. The .preferredColorScheme modifier reads the preference and applies it to the whole window immediately when it changes.

App/MovieGenreFilterApp.swift
import SwiftUI

@main
struct MovieGenreFilterApp: App {

    // Created once — lives for the entire app lifetime
    @State private var preferences = UserPreferences()

    var body: some Scene {
        WindowGroup {
            MovieListView()
                .environment(preferences)               // inject into tree
                .preferredColorScheme(preferences.preferredColorScheme) // live reaction
        }
    }
}

✅ How .preferredColorScheme works

Passing nil defers to the system. Passing .light or .dark forces that appearance for the whole hierarchy. Because preferences is @Observable, any Settings change immediately re-evaluates the modifier and SwiftUI redraws the scene.

Common mistakes

  • Creating a new UserPreferences inside the Settings screen.
  • Injecting the object after a screen that needs it.
  • Expecting .system to return a concrete colour scheme; it deliberately returns nil.

ViewModel Update MovieListViewModel — Add Search

Replace ViewModels/MovieListViewModel.swift with the version below. The key addition is a searchText property and a filteredMovies computed property. The View will iterate filteredMovies rather than movies.

⚠️ Why is filtering in the ViewModel?

The .searchable modifier only captures the text string — it does not filter data. Filtering is business logic, not presentation, so it belongs in the ViewModel. The View reads filteredMovies and never calls filter() itself.
ViewModels/MovieListViewModel.swift
import Foundation
import Observation

@Observable
final class MovieListViewModel {

    // In-memory data source — replaced by @Query in Part 3
    var movies: [Movie] = MockDataStore.movies

    // Bound to .searchable in the View
    var searchText: String = ""

    // Computed filtered list — View reads this, never `movies` directly
    var filteredMovies: [Movie] { filter(movies) }

    func filter(_ movies: [Movie]) -> [Movie] {
        guard !searchText.isEmpty else { return movies }
        return movies.filter {
            $0.title.localizedCaseInsensitiveContains(searchText)
        }
    }

    // Intent: toggle isWatched
    func markWatched(_ movie: Movie) {
        if let i = movies.firstIndex(where: { $0.id == movie.id }) {
            movies[i].isWatched = true
        }
    }

    // Intent: append from AddMovieView
    func addMovie(_ movie: Movie) {
        movies.append(movie)
    }

    // Intent: swipe-to-delete (works on filtered list)
    func deleteMovies(at offsets: IndexSet) {
        let filtered = filteredMovies
        for i in offsets {
            movies.removeAll { $0.id == filtered[i].id }
        }
    }
}

Common mistakes

  • Filtering the array directly inside MovieListView.
  • Using Movie.Genre. Genre is top-level.
  • Changing movies when you only mean to change the search query.

ViewModel AddMovieViewModel — Form State & Validation

Objective: keep form state and validation together, then convert valid form state into a Movie.

Create ViewModels/AddMovieViewModel.swift. Every form field has a matching property. The isFormValid computed property is the single source of truth for whether Save is allowed.

📐 Why a separate ViewModel?

The Add sheet has its own lifecycle. A dedicated ViewModel is created fresh each time the sheet opens and discarded on dismiss — exactly what @State gives us inside the sheet view. This keeps MovieListViewModel focused on list concerns only.

Key SwiftUI idea: @Bindable

An @Observable object can be stored in @State. When a view needs bindings such as $vm.title, create a local @Bindable reference inside body. This does not create a second ViewModel; it creates binding access to the existing observable object.

ViewModels/AddMovieViewModel.swift
import Foundation

@Observable
class AddMovieViewModel {

    // One property per form control
    var title         = ""
    var selectedGenre = Genre.action
    var rating        = 5.0
    var year          = Calendar.current.component(.year, from: Date())
    var synopsis      = ""
    var duration      = 120

    // Save button is disabled until all three conditions are met
    var isFormValid: Bool {
        !title.trimmingCharacters(in: .whitespaces).isEmpty &&
        !synopsis.trimmingCharacters(in: .whitespaces).isEmpty &&
        duration > 0
    }

    // Builds a Movie value from current form state
    func buildMovie() -> Movie {
        Movie(title: title, genre: selectedGenre, rating: rating,
              year: year, synopsis: synopsis, duration: duration)
    }
}

Common mistakes

  • Duplicating the validation rules in the Save button.
  • Creating a second genre enum for the form.
  • Building the Movie directly inside the View.

View AddMovieView — The Add Movie Modal

Objective: build a modal form that edits ViewModel state through bindings and reports a completed Movie back to its parent.

Create Views/Screens/AddMovieView.swift. The sheet owns an AddMovieViewModel via @State. When Save is tapped it calls the onSave closure passed in by MovieListView.

⚠️ Key pattern: @Bindable

@Observable objects do not provide $binding syntax automatically. Inside a View body (or a local scope) you must wrap the object: @Bindable var vm = viewModel. Then $vm.title produces a two-way Binding<String>. You will use this same pattern in Settings.
Views/Screens/AddMovieView.swift
import SwiftUI

struct AddMovieView: View {

    // Parent supplies this closure; result travels back via callback
    var onSave: (Movie) -> Void

    @Environment(\.dismiss) private var dismiss
    @State private var viewModel = AddMovieViewModel()

    var body: some View {
        @Bindable var vm = viewModel   // enables $vm.title etc.

        NavigationStack {
            Form {
                Section("Basic Information") {
                    TextField("Movie Title", text: $vm.title)
                        .textInputAutocapitalization(.words)

                    Picker("Genre", selection: $vm.selectedGenre) {
                        ForEach(Genre.allCases, id: \.self) { genre in
                            Label(genre.rawValue, systemImage: genre.icon).tag(genre)
                        }
                    }
                }

                Section("Details") {
                    Stepper("Year: \(viewModel.year)", value: $vm.year, in: 1900...2100)

                    VStack(alignment: .leading) {
                        HStack {
                            Text("Rating"); Spacer()
                            RatingView(rating: viewModel.rating)
                        }
                        Slider(value: $vm.rating, in: 0...10, step: 0.1).tint(.yellow)
                    }

                    Stepper("Duration: \(viewModel.duration) min",
                             value: $vm.duration, in: 1...500)
                }

                Section("Synopsis") {
                    TextEditor(text: $vm.synopsis).frame(minHeight: 100)
                }
            }
            .navigationTitle("New Movie")
            .navigationBarTitleDisplayMode(.inline)
            .toolbar {
                ToolbarItem(placement: .navigationBarLeading) {
                    Button("Cancel") { dismiss() }.foregroundColor(.red)
                }
                ToolbarItem(placement: .navigationBarTrailing) {
                    Button("Save") {
                        onSave(viewModel.buildMovie())
                        dismiss()
                    }
                    .fontWeight(.bold)
                    .disabled(!viewModel.isFormValid) // guarded Save
                }
            }
        }
    }
}

View SettingsSheetView — Appearance & Profile

Objective: read shared preferences from the environment and distinguish live state from draft state.

Create Views/Screens/SettingsSheetView.swift. It reads UserPreferences from the environment, offers a segmented picker for Light / Dark / System, and uses a draft pattern for the display name.

📐 Draft-then-commit pattern

The display name uses a local @State draft variable. Changes are committed to preferences.displayName only when Save is tapped — Cancel discards them cleanly. Appearance changes are live because the whole-window .preferredColorScheme modifier in the App entry point reacts immediately.
Views/Screens/SettingsSheetView.swift
import SwiftUI

struct SettingsSheetView: View {

    @Environment(UserPreferences.self) private var preferences
    @Environment(\.dismiss) private var dismiss

    // Local draft for the display name; appearance changes are applied immediately.
    @State private var draftName = ""

    var body: some View {
        @Bindable var prefs = preferences   // enables $prefs.colorSchemePreference

        NavigationStack {
            Form {
                Section("Profile") {
                    TextField("Display name", text: $draftName)
                }
                Section("Appearance") {
                    Picker("Theme", selection: $prefs.colorSchemePreference) {
                        ForEach(UserPreferences.ColorSchemePreference.allCases,
                                id: \.self) { mode in
                            Label(mode.rawValue, systemImage: mode.icon).tag(mode)
                        }
                    }
                    .pickerStyle(.segmented)
                }
            }
            .navigationTitle("Settings")
            .navigationBarTitleDisplayMode(.inline)
            .onAppear { draftName = preferences.displayName }
            .toolbar {
                ToolbarItem(placement: .navigationBarLeading) {
                    Button("Cancel") { dismiss() }
                }
                ToolbarItem(placement: .navigationBarTrailing) {
                    Button("Save") {
                        preferences.displayName = draftName
                        dismiss()
                    }.fontWeight(.semibold)
                }
            }
        }
    }
}

Why does the preview need .environment()?

@Environment(UserPreferences.self) looks up the object in the view's environment. Without an injected object, the preview cannot satisfy that dependency.

Common mistakes

  • Binding the display name directly to shared preferences when Cancel should discard edits.
  • Forgetting .environment(UserPreferences()) in the preview.
  • Assuming appearance changes must wait for Save; this tutorial deliberately makes them live.

View Update MovieListView — Toolbar, Search & Sheets

Objective: connect search, toolbar actions, sheets, navigation, and callbacks while keeping the screen responsible for orchestration rather than business logic.

Replace Views/Screens/MovieListView.swift with the full Part 2 version. Additions: .searchable bound to $vm.searchText, two toolbar buttons, and two .sheet modifiers.

Views/Screens/MovieListView.swift
import SwiftUI

struct MovieListView: View {

    @Environment(UserPreferences.self) private var preferences

    @State private var viewModel   = MovieListViewModel()
    @State private var showAddMovie = false
    @State private var showSettings = false

    private var navigationTitle: String {
        preferences.displayName.isEmpty
            ? "Movie List"
            : "\(preferences.displayName)'s Movies"
    }

    var body: some View {
        @Bindable var vm = viewModel   // needed for $vm.searchText

        NavigationStack {
            List {
                ForEach(viewModel.filteredMovies) { movie in
                    NavigationLink(
                        destination: MovieDetailView(
                            movie: movie,
                            onMarkWatched: { viewModel.markWatched($0) }
                        )
                    ) {
                        MovieRowView(movie: movie)
                    }
                }
                .onDelete { viewModel.deleteMovies(at: $0) }
            }
            .listStyle(.plain)
            .searchable(text: $vm.searchText, prompt: "Search movies…")
            .animation(.default, value: viewModel.filteredMovies.map { $0.id })
            .navigationTitle(navigationTitle)
            .toolbar { toolbarContent }
            .sheet(isPresented: $showAddMovie) {
                AddMovieView { viewModel.addMovie($0) }
            }
            .sheet(isPresented: $showSettings) {
                SettingsSheetView()
            }
        }
    }

    @ToolbarContentBuilder
    private var toolbarContent: some ToolbarContent {
        ToolbarItem(placement: .navigationBarTrailing) {
            HStack(spacing: 16) {
                Button { showAddMovie = true } label: {
                    Image(systemName: "plus")
                }
                Button { showSettings = true } label: {
                    Image(systemName: "gearshape")
                }
            }
        }
    }
}

✅ Why @ToolbarContentBuilder?

The .toolbar modifier expects a ToolbarContent result builder, not a plain View. Extracting it to a @ToolbarContentBuilder computed property keeps body readable and the toolbar independently scannable.

Common mistakes

  • Iterating over viewModel.movies instead of viewModel.filteredMovies.
  • Putting the Add Movie implementation inside the list screen.
  • Forgetting that the callback is the boundary between the sheet and the parent ViewModel.

Add Movie callback flow

📐 Callback data flow for Add Movie

MovieListView owns the list ViewModel. It passes an onSave closure when presenting AddMovieView. The sheet calls onSave(movie) → viewModel.addMovie(movie). The sheet never directly references the list ViewModel — communication flows only through the closure. This keeps both ViewModels fully decoupled.
